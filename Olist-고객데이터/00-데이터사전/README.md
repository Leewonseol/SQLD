# 데이터 사전: olist_customers_dataset.csv

`profile.py` 실행 결과를 근거로 작성했다. 아래 숫자는 전부 실제 파일을 읽어서 나온 값이며,
가정한 열이나 가정한 통계는 없다. CSV가 갱신되면 `python3 profile.py`를 다시 실행해 이 표를
갱신해야 한다.

## 2. 열 목록 (실제 헤더 그대로)

문서 앞부분에서 "예상되는 중심 열"로 제시된 5개와 실제 헤더가 **정확히 일치**함을 확인했다.

| 열 이름 | 원본 dtype(pandas 추론) | 실제 성격 | 결측 | 빈 문자열 |
|---|---|---|---|---|
| `customer_id` | object(str) | **주문 단위 식별자.** 이 파일에서 사실상의 PK(행수=유일값수=99,441) | 0 | 0 |
| `customer_unique_id` | object(str) | **사람 단위 식별자.** 유일값 96,096개로 행수보다 적음 → 1명이 여러 `customer_id`를 가질 수 있음 | 0 | 0 |
| `customer_zip_code_prefix` | object(str, 5자리 숫자문자열) | **지역 식별 코드.** 숫자로만 구성되어 있지만 선행 0을 포함할 수 있어 정수로 캐스팅하면 정보 손실 가능 — 크기 비교·산술 연산 대상 아님 | 0 | 0 |
| `customer_city` | object(str) | 범주형(자유입력 텍스트, 이미 소문자로 정규화됨) | 0 | 0 |
| `customer_state` | object(str, 2자리 알파벳) | 범주형(브라질 주 코드, 27개 값 = 26개 주 + 연방구 DF) | 0 | 0 |

## 3. 관측 단위(grain)와 PK/FK 후보

- **이 파일의 관측 단위는 "주문(order) 1건에 연결된 고객 스냅샷"이지, "사람 1명"이 아니다.**
  `customer_id`가 행마다 유일(99,441=99,441)하므로 이 파일 자체의 PK 후보는 `customer_id`다.
- `customer_unique_id`는 유일값이 96,096개로 행수보다 3,345개 적다. 즉 **3,345명의 실제
  고객(고유 사용자)이 2건 이상의 `customer_id`를 가진다.**
  - Olist 공식 데이터 설명에 따르면, orders 테이블에서 같은 사람이 다시 주문하면 새
    `customer_id`가 발급되고, `customer_unique_id`만 사람을 가로질러 동일하게 유지된다.
    즉 **`customer_unique_id`의 반복 등장 자체가 "재구매(repeat purchase)"의 증거**로
    해석할 수 있다 — 이는 임의로 만든 파생변수가 아니라 이 데이터셋의 설계 의도다.
- 반복 분포: 1회 93,099명, 2회 2,745명, 3회 203명, ... 최대 17회. 2회 이상(재구매 고객)
  2,997명(전체 고유고객의 3.12%).
- FK 후보: 이 파일만으로는 FK를 검증할 대상 테이블이 없다(§2 관계파일확인 참고). `customer_id`는
  (존재한다면) `orders.customer_id`를 참조하는 FK가 될 것으로 예상된다.

## 4. 결측·품질 이슈

이 CSV는 **결측치·빈 문자열이 전혀 없다**(5개 열 모두 null 0, empty string 0). 즉
"결측치 처리" 실습은 이 파일 자체에는 적용할 대상이 없다 — 없는 결측치를 억지로 만들어
처리하지 않는다.

문자열 정규화 상태도 이미 양호하다:
- `customer_city`: 대문자 0건, 앞뒤 공백 0건, 연속 공백 0건, 영소문자/숫자/하이픈/따옴표/공백
  이외 문자 0건(포르투갈어 억양 부호는 이미 제거되어 있음, 예: `sao paulo`).
- `customer_zip_code_prefix`: 전 행이 5자리 숫자 문자열, 비숫자 0건.

**따라서 "문자열 정제·대소문자/공백 정규화" 실습은 실제로 지저분한 값을 고치는 것이 아니라,
"이미 정규화되어 있음을 SQL로 검증하는" 실습이 된다.** `01-기본탐색`에서 이 사실 자체를
쿼리로 증명한다(멱등 정규화 함수를 적용해도 결과가 바뀌지 않음을 확인).

## 5. 참고: city는 단독 키가 아님

같은 도시 이름이 서로 다른 주(state)에서 163건 나타난다(브라질에는 동명 도시가 흔함).
따라서 지역 단위 집계·조인은 `customer_city` 단독이 아니라 `(customer_city, customer_state)`
조합 또는 `customer_zip_code_prefix`를 키로 써야 한다.

## 6. 이 파일로 정당화되는 파생변수 vs 금지되는 사용

| 파생/사용 | 허용 여부 | 근거 |
|---|---|---|
| `customer_unique_id`별 `customer_id` 등장 횟수(`n_orders`) | 허용 | 실제 행을 세는 것, Olist 설계상 재구매 신호로 문서화된 해석 |
| `n_orders > 1` → `is_repeat_customer` | 허용 | 위와 동일 근거의 이진 파생 |
| `customer_state`, `customer_city`를 범주형 변수로 사용 | 허용 | 원본 값 그대로 |
| `customer_zip_code_prefix`를 정수로 캐스팅해 크기 비교·회귀의 연속형 입력으로 사용 | **금지** | 우편번호는 식별/지역 코드이며 숫자 크기에 분석적 의미가 없음 |
| `customer_id`/`customer_unique_id`를 연속형 분석변수로 사용 | **금지** | 식별자 |
| 주문금액·배송기간·평점 등 이 파일에 없는 변수를 임의 생성 | **금지** | `03-기법별적용`에서 해당 기법은 "불가능"으로 보고하고 스켈레톤만 제공 |
